When the planner worker answers with an error (it crashed on the request, or found it malformed), is that an infeasible operation or an internal error?
I recommend an internal error of the simulation, because an infeasible operation makes the run replan and would hide a bug in the worker.

## Summary
AT 212 builds the client planner that sends each operation to a planner worker, a separate process for GPU or Linux planners. The worker answers in one of three ways: motion for every share, an infeasible operation with a reason from the closed list, or an error (`{"ok": False, "error": "internal_error", ...}`, the sim server's own error form). The ticket fixes only the unreachable worker: infeasible, no fallback. The build turns a worker error into an internal error of the simulate call, so the run controller stops and the person sees the worker's message. Treating it as infeasible would instead let the MRTAMP planner replan around a bug. Changing this later moves one branch in the client and one test.
