M · core cell and cell file · blocks removing the times from the cell file in AT 174, the station build · undo: a few hours
In what shape do the cell's times leave the cell file in this build: as an interim copy of today's flat time list in a travel-time table file, or only once AT 235 defines the table?
I recommend option A, an interim table file holding today's keys unchanged, because the cell file then breaks only once, as decided, and AT 235 reshapes only the new file.

## Background
The cell file describes the robot cell as JSON: robots, tools, stations, and today also a list of 20 times and feed rates (`timing`). That list is a field of the core cell type. Planners read tool-change and inspection times from it. The cell simulation, a separate repository, receives the cell over its wire and also reads tool-change and inspection times from that list.

The maintainer decided on 2026-10-19 that the cell description holds no times (recorded in ADR 0012). Travel and tool-change times go to a travel-time table file next to the cell file. Feed rates and offsets become skill parameters. On 2026-10-28 the maintainer approved AT 174 with "the move of `Cell.timing` to the per-cell travel-time table" in its scope.

## Scenario
The transformer cell's cell file holds `"timing": {"toolchange_time_at_toolstorage": 60.0, "inspection_time": 10.0, "feed_rate_milling": 1000.0, ...}`. A run sends the cell to the cell simulation. The simulation adds 80 s for each tool change and 10 s for each inspection from that list.

## Why this came up
The table's real shape (station-to-station legs) belongs to AT 235, the travel-time table build, which is still awaiting triage. AT 235 also removes the gym's own cell settings. Moving the times out now means choosing a file shape before AT 235, and changing the simulation's wire (it can no longer read `cell.timing`).
