How should B1, the greedy two-robot planner, split the 41 order-free battery lid screws between the two robots, when the sequence graph lists them as one fixed chain?
I recommend option A: B1 reads the screw groups the export already carries, and a robot may wait for a running step when it would still finish earlier, because this stays inside B1 and follows AT 143's decision that each planner reads the groups itself.

## Background
The sequence graph export of the battery holds the 41 lid screws as one chain in one arbitrary order (43 product states instead of 2^41). The graph attribute `collapsed_screw_groups` (the screws that may come out in any order) names the 41 screws as one group. AT 143 (2026-10-15) decided that each MRTAMP planner reads these groups itself. B1 does not read them yet. B1 lets two steps run at the same time only if they commute, that is, if the graph also holds them in the other order. In a chain, two screws never commute. B1 also prefers a robot that can start a step at once over a robot that would have to wait.

## Scenario
Battery, simulation's cell file with one screw nest plate per robot (built in this branch). Robot 1 inserts the lid. Robot 2 can screw, but its first screw must wait for the lid. Robot 1 is free and takes the next screw at once, and so on for all 41: Robot 1 screws 41, Robot 2 screws 0, simulated makespan about 1030 s. B1 never asks the simulation whether the two robots may screw together (zero feasibility checks). A probe in which same-group screws commute changes nothing: the lid stays Robot 2's blocker, and Robot 1 always wins.

## Why this came up
